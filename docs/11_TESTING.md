# 11. خطة الاختبارات (Testing Plan)

## ⚠️ لا أداة اختبار آلية — التحقق يدوي دائماً
هذا المشروع بلا `npm test`/`lint`/أي أداة بناء. كل تحقق يكون بفتح الملف فعلياً وتجربة السيناريو، **ويُفضَّل عبر خادم HTTP محلي وليس `file://` مباشرة** — `localStorage` مُعطَّل على أصل `file://`، وهو أساسي لعمل الجلسة (`mamelon_delegate_user`) وتخزين اختيار المنتج المؤقت (`mamelon_pending_products`).

```bash
# مثال: تشغيل خادم محلي بسيط من داخل مجلد المشروع
python -m http.server 8899
# ثم فتح http://localhost:8899/MANDOB%20GEMNI.html
```

## مسارات الاستخدام الحرجة (Critical Flows)
1. **تسجيل الدخول برمز PIN** — يجب أن يفشل بوضوح لرمز خاطئ، وينجح فوراً لرمز صحيح مسجَّل في `delegate_directory`.
2. **بحث + التقاط حالة** → التأكد أنها تختفي من قوائم المندوبين الآخرين فوراً (`current_holder` صار غير `null`).
3. **تسليم فردي** → التأكد من إدراج `deliveries` وتحديث `cases.status` وإرسال إشعار تليجرام (منذ 25 أغسطس 2026: عبر دالة `telegram-notify`، راجع `06_API.md` — يفشل الإشعار تحديداً وبصمت لو الأسرار غير مضبوطة على الدالة، بلا أي أثر على إدراج `deliveries`/تحديث `cases`).
4. **تسليم دفعة (منذ 25 أغسطس 2026):**
   - تحديد عدة حالات بنفس العيادة → التأكد من ظهور شريط الدفعة بالعدد الصحيح.
   - محاولة تحديد حالة من عيادة مختلفة أثناء تحديد قائم → يجب أن تُرفَض (الصندوق `disabled`).
   - تأكيد الدفعة بلا اختيار منتج لإحدى الحالات → يجب أن يُمنَع مع تنبيه واضح باسم الحالة الناقصة.
   - تأكيد دفعة كاملة صحيحة → تحقُّق SQL مباشر من `deliveries` (كل حالة بمنتجها الصحيح + نفس المستلم) و`cases.status` (كل الحالات `delivered`).
   - **اختبار عمليتَي دفعة متتاليتين، لا واحدة فقط** — عطل ADR-C02 لم يظهر إلا بعد دفعة ثانية.
5. **إرجاع حالة** → التأكد من إدراج `returns` وأن الحالة ترجع لـ`ready` لا `registered`.

## ملاحظات اختبار مهمة (من تجارب فعلية)

1. عند اختبار أي تعديل بواسطة وكيل ذكاء اصطناعي عبر متصفح آلي: **تحقَّق أن الصفحة حصلت على أصل HTTP حقيقي (`http://localhost:...`) لا معاينة "لقطة ثابتة" (`data:` URL)** — بعض أدوات المعاينة تحوّل الملفات المحلية خارج مجلد مشروع معروف إلى لقطة ثابتة تلقائياً، وهذا يُعطِّل `localStorage` بصمت (خطأ `SecurityError: Storage is disabled inside 'data:' URLs`) ويجعل أي اختبار لتسجيل الدخول أو تخزين مؤقت يفشل بسبب غير متعلق بالكود إطلاقاً.

2. **عند اختبار أي Edge Function أو API عبر `curl` من Bash على ويندوز، لا تمرّر نصاً عربياً (أو أي UTF-8 غير ASCII) كوسيطة `-d`/`--data` مباشرة بسطر الأمر** — طرفية ويندوز (حتى داخل Git Bash) تكسر ترميز UTF-8 لوسائط سطر الأوامر العربية قبل ما تصل لـ`curl` أصلاً، فتظهر النتيجة مشوَّهة عند الطرف المستقبِل (مثال حقيقي: ADR-C03 في `10_DECISIONS.md`) رغم أن الكود الفعلي (`fetch`+`JSON.stringify` من متصفح حقيقي) سليم تماماً ولا يعاني من نفس المشكلة. **الحل:** اكتب حمولة الطلب لملف UTF-8 أولاً، وأرسلها بـ`curl --data-binary @<مسار الملف>`.

3. **GitHub Pages للريبوهات الخاصة (Private) غير متاح على حساب GitHub المجاني الشخصي.** إن كان الريبو خاصاً وقت تفعيل إعدادات Pages، **لن تُبنَى أي نسخة إطلاقاً** بغض النظر عن صحة الإعدادات المعروضة (`Deploy from branch: main/root` قد تظهر صحيحة تماماً بينما الصفحة الفعلية "Site not found"). تحقَّق من هذا عبر `GET /repos/<owner>/<repo>/actions/runs` — لو `total_count: 0` فمعناها لم يُبنَ شيء أبداً. **بعد تحويل الريبو لعام، لازم دفعة (`push`) جديدة لتشغيل أول بناء** — تغيير الأهلية وحده لا يُشغِّل بناءً تلقائياً؛ `git commit --allow-empty` كافٍ لهذا الغرض لو لا يوجد تعديل حقيقي جاهز للدفع.

4. **تجنَّب المسافات في أسماء الملفات المستضافة عبر GitHub Pages إن كان الرابط سيُستخدَم بأداة تغليف PWA→APK خارجية** (مثل WebIntoApp) — بعض هذه الأدوات لا تتعامل بشكل موثوق مع ترميز `%20`، حتى لو الرابط يعمل تماماً عند فتحه مباشرة بمتصفح عادي. تسمية الملف الرئيسي `index.html` (يُفعِّل الرابط الجذري البسيط بلا أي اسم ملف ظاهر بالرابط أصلاً) هو الحل الأكثر أماناً وتوافقاً.
